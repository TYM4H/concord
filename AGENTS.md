# Concord

## Назначение

Разрабатывай Concord как локальное веб-приложение для аналитика, которому нужно найти одну и ту же сущность в двух реляционных базах. Основной рабочий сценарий — найти людей, присутствующих в обоих источниках. Логику сопоставления делай пригодной и для других сущностей, например организаций из CRM и ERP. Не закладывай обязательный тип сущности, набор колонок или формат имени.

## Пользовательский сценарий

Аналитик подключает два источника в режиме чтения и выбирает с каждой стороны таблицу и столбец идентификатора. Эти два выбора задают сущности, между которыми ищутся соответствия. Значения ID нужны для адресации записей и выдачи результата. Одинаковые номера в независимых базах сами по себе ничего не доказывают.

Приложение изучает схемы и доступные значения, предлагает сопоставимые признаки и показывает примеры. Аналитик может подтвердить предложение, заменить поле, уточнить связь или исключить сомнительный признак. Предусмотри работу с PostgreSQL и MySQL, в том числе когда источники используют разные СУБД. Для обычного сценария достаточно интерфейса приложения, без предварительной подготовки SQL пользователем.

Перед реализацией экрана изучи доступный фрейм, состояния и переходы. Сохраняй стиль, навигацию и основные элементы управления. Компоновку можно адаптировать под задачу аналитика и реальные данные. Если Figma недоступна, в `docs/screens/` есть снимки пяти основных экранов.

В обсуждении макетов выделены следующие разделы. Уточняй фактические названия и расположение действий по Figma.

| Раздел | Задача пользователя |
| --- | --- |
| Обзор | Понять текущее состояние работы и перейти к сопоставлению. |
| Источники данных | Подключить базы, проверить доступ и посмотреть таблицы, поля и связи. |
| Сопоставление | Выбрать два ID, проверить предложения по полям, запустить обработку, разобрать результаты и выгрузить соответствия. |
| Правила | Просмотреть и скорректировать используемые признаки, нормализацию и условия принятия решений. |

Пример с организациями в макете иллюстрирует сценарий. Подписи и значения, зависящие от конкретной базы, подставляй из выбранных источников. Если для функции нет состояния в Figma, используй существующие компоненты и явно обозначь принятое решение.

## Логика сопоставления

В MVP используй объяснимые алгоритмы без нейросетей. Предлагай поля с учётом типов, названий, примеров и распределения значений. Разрешай проход по нескольким связанным таблицам. Показывай путь от выбранного ID до признака. Для связей многие-ко-многим сохраняй несколько значений у сущности. Повтор строки после соединения таблиц не должен усиливать доказательство. Если связь отсутствует в схеме или её смысл неоднозначен, дай аналитику уточнить её.

Нормализуй значения по правилам, подходящим для конкретного поля. Сохраняй связь нормализованного значения с оригиналом. Учитывай пропуски, противоречия и частоту значений. Общий признак, встречающийся у тысяч сущностей, даёт мало оснований для совпадения. Возможные дубли сохраняют исходные ID. Не навязывай соответствие один к одному.

## Результат и объяснения

Для каждой предложенной пары возвращай оба исходных ID, статус и основания решения. В интерфейсе должно быть видно, откуда получены значения, как они изменились при нормализации, какие сравнения поддерживают или ослабляют совпадение и какое правило определило статус. Формируй объяснение из результата фактически выполненных сравнений.

Различай автоматически принятые пары, кандидатов на ручную проверку и записи без найденной пары. Аналитик может подтвердить или отклонить кандидата. Сохраняй ручное решение отдельно от автоматического. Выгрузка должна позволять использовать пары ID в дальнейшей работе и проследить основания связи.

## Среда и масштаб

Интерфейс и обработка работают на машине аналитика. Для выполнения сопоставления достаточно доступа к двум указанным базам. Исходные записи и учётные данные не отправляй внешним сервисам. Не изменяй данные или схемы источников. Настройки, результаты и ручные решения храни локально, пароли не записывай в журналы.

Ориентир — около миллиона записей с каждой стороны. Отбирай кандидатов до подробного сравнения, избегай полного декартова произведения. Обрабатывай большие выборки порциями и показывай результаты постранично. Заявления о скорости, объёме и точности основывай на измерениях.

## Работа в репозитории

Сохраняй модульные границы между источниками, правилами сопоставления, обработкой запусков и интерфейсом. PostgreSQL и MySQL — первые серверные СУБД. При добавлении нового источника проверяй чтение схемы, ключей и записей в его диалекте. Общий алгоритм сопоставления должен работать независимо от драйвера.

Учитывай структуру и соглашения репозитория. Выбирай простой стек для локального запуска и проверяй изменения через рабочий пользовательский сценарий. Не делай наличие реальных баз, размеченных пар или заранее подготовленных демонстрационных примеров условием начала разработки. Такие наборы будут подбираться отдельно для проверки и доработки продукта.
