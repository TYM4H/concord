# Миллион записей в PostgreSQL и MySQL

19 ноября 2026 года на macOS 26.2 (arm64), Python 3.13.2, SQLite 3.49.1, PostgreSQL 14.17 и MySQL 8.0.41. Оба сервера работали локально через Unix-сокеты. Один последовательный прогон каждой версии, те же источники, новый каталог Concord для каждого запуска. Между прогонами кэш ОС и серверов сохранялся.

## Данные и контроль

Слева миллион строковых ID с ведущими нулями в `registry.people`. Имя берётся из самой таблицы, почта из `registry.contacts` через внешний ключ. Поэтому Concord получает из PostgreSQL два миллиона строк проекции на миллион людей. Справа миллион целочисленных ID в `customers`, оба признака в той же таблице. Имена сравниваются после нормализации с весом 70, почта точно с весом 30. Пороги проверки и принятия равны 65 и 85.

Одна пара в очереди подтверждена вручную. Проверены все 250 001 строк CSV, в том числе исходные ID, их типы, основания принятия и исходы сравнений. Файл занимает 258 751 261 байт. В результатах по 500 000 записей без пары с каждой стороны. Проверены все исходные ID и причины отсутствия пар. Все 1 500 000 строк результата, включая объяснения, побайтно совпали у двух версий. Изменились распределение значений, алфавит имён, объём объяснений и полнота журнала сравнений. Из этих измерений нельзя выделить вклад одной причины. Дополнительные скачивания уже сохранённых результатов на одной версии в порядке A–B–B–A заняли 4,75 и 4,41 с для A, 17,42 и 15,83 с для B. Все четыре файла совпали по SHA-256 с соответствующими исходными CSV.

Concord сравнил 1 750 064 пары. Проверка прошла по каждому исходному ID, статусу и баллу. В результат попали ровно 1 000 000 размеченных связей, в том числе обе связи для каждой из 250 000 записей с дублями. Из них 249 992 связи приняты автоматически, 750 008 направлены на проверку. Все 750 064 сравнения ниже порога сверены с ожидаемыми ID и баллами в диагностическом снимке.

У записи `0000001` в интерфейсе рядом показаны `1000001` и `1000002` с баллом 66,82 и `1000003` с баллом 17,32. Первые два ID независимо подтверждены и сохранились после перезапуска. У записи `0000002` проверены все десять ID на двух страницах. Выгрузка содержит 249 994 связи и занимает 266 244 011 байт. Каждая строка проверена по разметке, включая основания принятия.

## Что изменилось

- Порядок ключей временного индекса позволяет SQLite считать частоты общим проходом. Первичный ключ одновременно устраняет повторы одного нормализованного значения у сущности.
- Левые сущности, исходные значения и частоты теперь читаются одним упорядоченным запросом. Обработка сохраняет сущности с пустыми признаками.
- При экспорте SQLite объединяет два упорядоченных потока из индексов — автоматически принятые и подтверждённые вручную. Основания связи передаются в CSV без повторной сериализации в Python.
- При возврате в историю Concord сверяет SHA-256 файла запуска и читает сохранённые счётчики из индекса. Для JSONL размером 814 МиБ получение списка запусков с пустым кэшем приложения заняло 5,60 и 5,34 с до изменения, 0,40 и 0,33 с после. Этот замер выполнен отдельно от первого открытия результатов.

## Повторение

На отдельных тестовых серверах с ролью `concord_reader` выполните [скрипт для PostgreSQL](fixtures/million_postgresql.sql) через `psql` и [скрипт для MySQL](fixtures/million_mysql.sql) через `mysql`. Скрипты создают новую базу `concord_million_01` в каждой СУБД. Подготовьте два обычных JSON-профиля Concord с доступом на чтение. Для PostgreSQL укажите схему `registry` и таблицу `people`, для MySQL схему `concord_million_01` и таблицу `customers`. При необходимости передайте пароли через `CONCORD_LEFT_PASSWORD` и `CONCORD_RIGHT_PASSWORD` в окружении сервера.

В первом терминале из корня проекта запустите измеряемый просмотрщик в новом каталоге.

```sh
.venv/bin/python -m benchmarks.relational --workspace local-runs/million-repeat --port 8766
```

Во втором терминале укажите пути к двум профилям и тот же каталог.

```sh
.venv/bin/python -m benchmarks.million_workflow http://127.0.0.1:8766 \
  /path/to/postgresql.json /path/to/mysql.json local-runs/million-repeat
```

В каталоге останутся `stages.json` с фазами сервера, `workflow.json` с клиентскими замерами, JSONL запуска, базы проверки и диагностики и `accepted.csv`. Финальный набор файлов занимает около 2,44 ГиБ. Для ещё одного прогона используйте новый каталог и перезапустите измеряемый просмотрщик.

## Полные тёзки, опечатки и пропуски в почте

В этом тесте заранее размечены 850 000 пар. В обоих источниках присутствуют 800 000 человек. У 50 000 из них справа есть дополнительная запись. Ещё 200 000 человек есть только слева и 150 000 только справа. Исходные ID перемешаны. Разметка доступна только программе оценки.

PostgreSQL и MySQL сформировали синтетические ФИО и адреса запросами на чтение по миллиону ID из таблиц набора `concord_multi_01`. Среди левых записей 824 162 человека делят полное ФИО хотя бы с одним другим человеком в этом же источнике. У 55 335 левых и 110 557 правых записей почта отсутствует. У 23 260 левых и 72 411 правых адресов переставлены буквы в домене. Генератор также моделирует смену адреса, общие почтовые ящики и опечатки в фамилии. Частоты заданы для сравнения алгоритма на синтетических данных.

Обе версии прошли отбор кандидатов и оценку пар в ядре Concord на одном индексе. Вес ФИО равен 70, вес почты — 30. Нижняя граница возможного совпадения равна 65, порог автосовпадения — 66,82. Между прогонами менялось только действие при расхождении заполненных адресов.

В `comparison.json` сохраняются показатели, настройки и примеры с обоими ID. Для экономии места временный индекс SQLite хранится в памяти.
